# 多虚拟屏支持可行性方案

> 状态：**设计提案（未实现）**
> 适用工程：ManagedFloatingApp
> 目标：从当前「单虚拟屏 + 单前台 App」升级为「N 个虚拟屏，各自独立承载/截帧/注入」。
> 约束沿用总纲：免 root、arm64-v8a、minSdk 24、仅局域网/USB、敏感信息不入档。

---

## 1. 背景与目标

### 1.1 现状（代码事实）
当前为**严格单屏架构**：

- `VdHelper` 启动时只调用一次 `DisplayManager.createVirtualDisplay("mfa-agent", ...)`，写死一块屏。
- `AppScreenController` 只持有单个 `@Volatile var vdSession: VdSession? = null`，无集合容器。
- 文件 IPC 只有**单对** `cmd.txt / result.txt`，`ready.txt` 里只有一个 displayId。
- 所有操作（launch/frame/tap/swipe）都隐式作用于这唯一一块屏。
- `app_launch` 每次把新 App `am start --display <同一个 id>` 拉到同一块屏，后启动者覆盖前者成为前台。

结论：**当前最多 1 个虚拟屏，同一时刻仅 1 个前台承载 App**（可切换，可对设备上全部可启动 App 反复 launch，数量无应用层人为上限）。

### 1.2 目标
- 支持同时创建并管理多块虚拟屏，数量可配置（建议默认上限 4，硬上限见 §6 资源评估）。
- 每块屏独立：承载 App、截图、触摸注入、生命周期。
- REST / MCP / 自动化脚本全链路以 `displayId`（或逻辑 `slotId`）区分目标屏。
- 保持免 root、不引入新原生依赖、向后兼容现有单屏调用。

### 1.3 非目标
- 不做跨屏拖拽、屏间 App 迁移（可列为后续增强）。
- 不做多屏音频路由。
- 不做 WebRTC（仍为 MJPEG，二期再议）。

## 2. 现状架构与关键约束

### 2.1 组件链路
```
App 进程 (uid=app)
  └─ AppScreenController ── 单个 VdSession ── 文件 IPC（cmd/result/ready）
                                        │
adb over TLS (NoRootShell, held pty)    │
                                        ▼
shell 助手 (uid=2000, app_process ... VdHelper)
  └─ shell 包上下文 DisplayManager ── createVirtualDisplay ×1
        └─ ImageReader ×1（RGBA_8888, maxImages=2）
```

### 2.2 已验证的硬约束（来自 M1~M5 真机结论）
1. **必须 shell/uid=2000 上下文**才能建 trusted 虚拟屏（app uid 建的屏无法承载第三方 App）。
2. **MIUI 会话保活**：adbd 关闭会话会杀进程组，`setsid` 无效；必须由 App 持有 pty 流（`NoRootShell.helperStream`）维持 `VdHelper` 存活。
3. **文件 IPC 已加 `ipcLock` 串行化**（单通道）；多屏后通道数增加，需重新设计隔离。
4. **静态画面 ImageReader 无新帧**：已用「缓存最后一帧」解决，多屏需每屏独立缓存。
5. **截图 rowStride/pixelStride 处理**已修复（去 padding 防撕裂），多屏复用同一套 `renderPng`。
6. **seq 单调 + 回绕重置**机制已存在，多通道需各自维护 seq。

## 3. 方案选型

### 方案 A：单 VdHelper 管理多 VirtualDisplay（推荐）
一个常驻 `VdHelper` 进程内持有 `Map<displayId, DisplayContext>`，每个 context 含独立 `VirtualDisplay + ImageReader + 帧缓存`。

- 优点：只维持一条 pty 保活流；共享 shell 上下文与 Looper；进程/内存开销最小；集中调度。
- 缺点：单进程内多 ImageReader 并发，需要清晰的线程模型；helper 崩溃影响所有屏（需看门狗重启 + 状态重建）。

### 方案 B：每屏一个 VdHelper 进程
每个虚拟屏拉起独立 `app_process ... VdHelper <slot>`。

- 优点：故障隔离强；IPC 天然按进程分目录。
- 缺点：每条 pty 都要保活，MIUI 上多会话被回收概率叠加；多份 ART/类加载内存成本高；管理复杂。**不推荐作为首选**。

### 结论
采用 **方案 A**，方案 B 仅作为未来「强隔离」场景的备选。

## 4. 详细设计（方案 A）

### 4.1 数据模型

```kotlin
/** 一块虚拟屏的运行时句柄，集中在 VdHelper 内。 */
data class DisplayHandle(
    val slotId: Int,            // 逻辑槽位 0..N-1，稳定标识
    var displayId: Int = -1,    // 系统分配，重建后可能变化
    val width: Int, val height: Int, val dpi: Int,
    val virtualDisplay: VirtualDisplay,
    val imageReader: ImageReader,
    @Volatile var lastFrame: ByteArray?,   // 每屏独立静态帧缓存
    var currentPackage: String? = null,
)
```

App 侧会话集合：
```kotlin
// AppScreenController
private val sessions = ConcurrentHashMap<Int, VdSession>()   // key = slotId
fun session(slotId: Int): VdSession? = sessions[slotId]
```

> 用 **slotId（逻辑稳定）** 对外，**displayId（系统易变）** 对内。会话/助手重启后 displayId 会变，slotId 不变，便于恢复与持久化。

### 4.2 IPC 协议扩展（向后兼容）

现有协议：`<seq>|<op>|<args...>`，单对 `cmd.txt/result.txt`。

**扩展为按 slot 分通道**，目录：
```
<filesDir>/mfa/
  global/ready.txt                 # 助手就绪 + 全局信息
  slot-0/cmd.txt  result.txt  frame.png
  slot-1/cmd.txt  result.txt  frame.png
  ...
```

命令字增加 slot 维度（首字段后插 slot）：
```
<seq>|<op>|<slotId>|<args...>
```
- 新增管理命令：
  - `create|<slot>|<w>|<h>|<dpi>` → 建屏，回 `displayId`
  - `destroy|<slot>` → 销毁并回收
  - `list` → 回所有 `slot:displayId:pkg`
- 现有 `launch/frame/tap/swipe/key` 改为带 slot：
  - `launch|<slot>|<component>`
  - `frame|<slot>|<path>`
  - `tap|<slot>|<x>|<y>`
  - `swipe|<slot>|<x1>|<y1>|<x2>|<y2>|<durMs>`

**兼容策略**：保留旧的无 slot 命令作为 `slot-0` 的别名，旧客户端/自动化脚本不改也能跑。

每 slot 独立 `seq`、独立锁（`Map<slot, Any>`），避免跨屏互相阻塞；helper 侧用单线程命令队列顺序处理，避免 ImageReader 并发竞争。

### 4.3 VdHelper 改造要点
- 启动时不再立即建屏，改为等待 `create` 指令（或按参数批量预建 N 块）。
- 维护 `Map<Int, DisplayHandle>`；每个 ImageReader 用独立 handler thread 或统一单线程 executor。
- `captureFrame(slot)`：复用现有 stride 修正 + lastFrame 缓存逻辑，按 slot 存取。
- 注入命令拼接 `input -d <displayId> ...` / `am start --display <displayId> ...`，displayId 从 handle 取。
- 增加看门狗：若某 ImageReader 长时间无帧且非静态场景，标记该 slot 异常并支持单屏重建。
- `quit` 前销毁所有 VirtualDisplay、close 所有 ImageReader，防 Surface 泄漏。

### 4.4 控制器 / API 改造

`ScreenController` 接口增加带 slot 的重载（保留旧签名 = 默认 slot 0）：
```kotlin
fun launch(slot: Int, pkg: String, component: String?): LaunchResult
fun captureFrame(slot: Int): ByteArray?
fun tap(slot: Int, x: Int, y: Int): Boolean
fun swipe(slot: Int, x1: Int, y1: Int, x2: Int, y2: Int, durMs: Int): Boolean
fun createDisplay(slot: Int, w: Int, h: Int, dpi: Int): Boolean
fun destroyDisplay(slot: Int): Boolean
fun listDisplays(): List<DisplayInfo>
```

REST（新增，旧路径保留等价于 slot 0）：
```
POST /displays                       创建  {"slot":1,"width":720,"height":1560,"dpi":400}
GET  /displays                       列出所有屏与当前承载包
DELETE /displays/{slot}              销毁
POST /displays/{slot}/launch         {"packageName":"..."}
GET  /displays/{slot}/frame          PNG
POST /displays/{slot}/action/tap     {"x":..,"y":..}
POST /displays/{slot}/action/swipe
GET  /displays/{slot}/stream         每屏独立 MJPEG
```

MCP：现有 9 工具的 arguments 增加可选 `slot`（默认 0），并新增：
- `display_create` / `display_destroy` / `display_list`。

### 4.5 配置与持久化
`ServerConfig` 增加：
- `maxDisplays`（默认 4）；
- `autoCreateSlots`（重启后自动重建的槽位规格列表）。
持久化每 slot 的规格与上次承载包，配合现有「会话自动恢复」在助手重启后批量 `create` + 重新 launch。

### 4.6 生命周期与故障恢复
- App 进程重启 → 现有 auto-resume 扩展为：连 adbd → 拉起 helper → 按持久化规格逐 slot 建屏 → 恢复承载。
- helper 崩溃 → pty 流断开被感知 → 整体重建所有 slot（单 helper 方案的代价），通过 lastFrame 与任务队列降低中断影响。
- 单屏异常 → 支持只重建该 slot，不影响其他屏。

## 6. 资源与系统限制评估

### 6.1 单屏内存估算（720×1560 RGBA_8888）
- 单帧像素：`720 × 1560 × 4 ≈ 4.49 MB`
- ImageReader `maxImages=2`：≈ **9 MB** GPU/图形缓冲
- 加 lastFrame PNG 缓存（编码后约 0.07~0.12 MB，可忽略）与 VirtualDisplay/Surface 开销

### 6.2 多屏粗估（仅图形缓冲，不含被承载 App 自身内存）
| 屏数 | ImageReader 缓冲下限 |
|------|----------------------|
| 2 | ≈ 18 MB |
| 4 | ≈ 36 MB |
| 8 | ≈ 72 MB |

> 真正的大头是**每个被承载 App 自己的进程内存**（Activity/View/图片缓存），与 App 类型强相关，需真机压测。helper 侧图形缓冲相对可控。

### 6.3 系统/ROM 限制
- Android 对单进程/全局 VirtualDisplay 数量无固定公开常量，实际受 SurfaceFlinger、Gralloc、GPU 内存约束，MIUI 等 ROM 可能更保守。
- **建议默认上限 4**，提供配置项；通过真机压测确定该设备安全值（监控 `dumpsys SurfaceFlinger`、内存、帧率、建屏失败率）。
- 多 trusted display 的焦点策略（`FLAG_OWN_FOCUS` 等，SDK34+）需验证；SDK33 焦点行为需实测。

## 7. 风险与对策

| 风险 | 等级 | 对策 |
|------|------|------|
| 单 helper 崩溃拖垮全部屏 | 高 | pty 看门狗 + 自动整体重建 + 规格持久化；必要时演进到方案 B |
| 多 ImageReader 并发取帧竞争/花屏 | 中 | 单 executor 串行取帧；复用已验证的 stride 修正与帧缓存 |
| 文件 IPC 多通道串扰 | 中 | 按 slot 分目录、独立 seq 与锁；保留 slot-0 兼容别名 |
| 内存/GPU 超限建屏失败 | 中 | maxDisplays 门控 + 建屏失败明确错误码 + 真机压测定上限 |
| MIUI 多屏焦点/输入注入异常 | 中 | 逐真机验证 `input -d`、焦点 flag；保留单屏可用降级路径 |
| displayId 重启变化导致外部引用失效 | 低 | 对外只暴露稳定 slotId，内部映射 displayId |
| 向后兼容破坏旧自动化脚本 | 低 | 旧无 slot 命令/路由全部映射到 slot 0 |

## 8. 分阶段落地计划

- **阶段 0（基线/无功能改动）**：抽离 `renderPng`、帧缓存、IPC 序列化等为可复用组件；补单测。
- **阶段 1（双屏 POC）**：VdHelper 支持 2 个 slot，分目录 IPC，`create/destroy/list`；真机验证双屏各自 launch/capture/tap。
- **阶段 2（API 贯通）**：`/displays/*` REST + MCP slot 参数与管理工具；MJPEG 多通道；并发上限改为全局总路数。
- **阶段 3（持久化与恢复）**：规格持久化、重启批量重建、单屏/整体看门狗恢复。
- **阶段 4（打磨）**：首页多屏管理 UI、压测确定 `maxDisplays` 默认值、文档与全量回归。

每阶段都按现有规范产出真机验证记录与评审报告，遵循 Conventional Commits。

## 9. 验收标准（建议）

1. 单设备可同时创建 ≥2 块虚拟屏（目标 4），各自独立承载不同 App 且截图内容正确无撕裂。
2. 对任一 slot 的 tap/swipe 只作用于对应屏，互不干扰。
3. 每屏独立 MJPEG 流可同时播放，全局并发路数受门控（超限 503）。
4. 杀掉/重启 helper 后，所有 slot 能按持久化规格自动恢复承载。
5. 旧的单屏 REST/MCP/自动化脚本调用在不改动的情况下仍正常（slot 默认 0）。
6. 单元测试覆盖 slot 路由、seq 隔离、配置门控；真机多屏用例全部通过。
