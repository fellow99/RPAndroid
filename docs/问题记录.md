## 1. 现象

承载任意被托管 App（计算器 / 天气 / 日历等）到虚拟屏后，调用：

- MCP `ui_read`
- REST `GET /ui`（等价）

返回的元素树里**没有任何 `displayId != 0` 的窗口**，只有 `displayId=0` 的**主屏**内容（状态栏 clock / 星期 / 电池 / WLAN / 通知图标等 `com.android.systemui` 元素），被托管 App 的按钮、文本、输入框一个都读不到。

## 2. 复现步骤与实测证据

| 步骤 | 操作 | 结果 |
|---|---|---|
| 1 | 建立托管会话（`status.sessionActive=true`），承载「计算器」 | `hostedApp=计算器`，`/frame`、`screen_capture` 正常出帧 |
| 2 | 调用 `ui_read` | 返回 **4701 字节**，元素全部 `"displayId":0`，例：`{"text":"12:25","className":"android.widget.TextView","packageName":"com.android.systemui",...}`、`{"text":"11月9日 周一",...}`、`{"text":"正在充电，已完成 92%",...}` |
| 3 | 在主屏 App（如设置）导航 | `/ui` 能正常读到主屏其它应用元素（`displayId=0` 覆盖主屏当前窗口） |
| 4 | 结论 | 无障碍窗口列表**只包含默认（主）屏窗口**，虚拟屏窗口未进入 |

> 注：撰写本文档时真机不在线（无 ping / mDNS / adb），未能在当日重抓 `dumpsys` 取证；以上证据取自当天实测输出，复现口径已固定，下次联调即可重放。

## 3. 源码链路（代码事实）

读取路径（操作单一入口，见宪法 C-1）：

```
MCP ui_read / REST GET /ui
  → core:server ManagedServer.get("/ui")    核心只做转发
  → ScreenController.readUi()                核心控制器
  → AppScreenController.uiReader             app 注入的回调
  → MfaAccessibilityService.instance?.dumpUi()
```

`MfaAccessibilityService.dumpUi()`（`app/src/main/java/com/managedfloating/app/a11y/MfaAccessibilityService.kt`）：

```kotlin
val windows = runCatching { windows }.getOrNull() ?: emptyList()   // AccessibilityService.windows
for (w in windows) {
    val root = runCatching { w.root }.getOrNull() ?: continue
    val displayId = if (Build.VERSION.SDK_INT >= 30) w.displayId else -1
    collect(root, out, displayId)
}
if (out.length() == 0) rootInActiveWindow?.let { collect(it, out, -1) }  // 兜底也只到主屏
```

- 元素来源**完全依赖 `AccessibilityService.windows`（`getWindows()`）**；`getWindows()` 不给虚拟屏窗口，`dumpUi` 就无数据。
- `rootInActiveWindow` 兜底只对应“活动窗口”，而“活动窗口”概念在主进程视角仍指默认屏，兜底也拿不到虚拟屏。

服务配置（`app/src/main/res/xml/accessibility_service_config.xml`）：

```xml
android:accessibilityEventTypes="typeWindowStateChanged|typeWindowContentChanged"
android:accessibilityFlags="flagDefault|flagRetrieveInteractiveWindows|flagIncludeNotImportantViews"
android:canRetrieveWindowContent="true"
```

- 已开 `FLAG_RETRIEVE_INTERACTIVE_WINDOWS` 与 `FLAG_INCLUDE_NOT_IMPORTANT_VIEWS`，即“交互窗口 + 不重要视图”都已尽力，仍读不到虚拟屏 ⇒ 问题不在本服务配置，而在上游（系统/ROM）没把虚拟屏窗口喂给无障碍栈，或虚拟屏类型被 a11y 排除。

宿主侧虚拟屏创建（`core/shell/.../vd/VdHelper.kt`），关键事实：

```kotlin
// 注意：不使用 FLAG_PUBLIC——公开虚拟屏会被系统当作投屏/演示屏，从而触发 ROM 的投屏保护……
val flags = FLAG_OWN_CONTENT_ONLY or FLAG_SUPPORTS_TOUCH or
            FLAG_ROTATES_WITH_CONTENT or FLAG_DESTROY_CONTENT_ON_REMOVAL or FLAG_TOUCH_FEEDBACK_DISABLED
// sdk >= 30 追加：FLAG_TRUSTED | FLAG_OWN_DISPLAY_GROUP | FLAG_ALWAYS_UNLOCKED
// sdk >= 34 追加：FLAG_OWN_FOCUS | FLAG_STEAL_TOP_FOCUS_DISABLED
```

- 虚拟屏是 **PRIVATE（非 PUBLIC）** 私有虚拟屏 + `OWN_CONTENT_ONLY`。
- 触摸注入走 `input -d <displayId> tap|swipe|keyevent` 可用、截帧可用 ⇒ **WMS 层面窗口确实存在**，只是**无障碍（a11y）层没暴露**。

## 4. 根因分析（分层假设，需逐一取证）

核心矛盾：**“窗口存在（能截图、能注入触摸）但无障碍读不到”**。可能原因按层次列出：

### 假设 A（最可能）：ROM 的 AccessibilityManagerService 只维护默认屏窗口列表

- MIUI 基于 AOSP Android 13 裁剪，其无障碍窗口跟踪（`AccessibilityWindowManager` / 各显示窗口的回调注册）很可能只处理 `displayId=0`。
- 表现与本问题完全一致：`AccessibilityService.windows` 只返回主屏窗口，虚拟屏从不出现。
- 佐证 1：同会话其它 ROM 行为 **A/B 差异未知**（需在非 MIUI/原生 13 设备复测）。
- 佐证 2：规格 `101-main-ui/spec.md §9.1` 已记录同一 ROM 的“投屏保护”策略（承载「设置」时触发 `mForceHideNonSystemOverlayWindow=true`，浮窗被系统隐藏）——说明 **MIUI 的 WindowManager 对“非主屏/虚拟屏相关窗口”有系统性策略干预**，无障碍层被一并裁剪是同一策略家族。

### 假设 B：PRIVATE + OWN_CONTENT_ONLY 虚拟屏被 WMS 跳过无障碍窗口注册

- AOSP `WindowManagerService` 对 display 窗口会向 a11y 控制器注册 / 或按“public vs private”决定是否对无障碍开放。
- 当前实现刻意用 **PRIVATE**（避免投屏保护 → 见规格 §9.1 的 PUBLIC/PRIVATE 权衡），代价可能是**被 a11y 排除**。
- 若把虚拟屏改为 **PUBLIC**，a11y 可能可见，但会重新触发 ROM 的投屏/悬浮窗策略（回到规格 §9.1 的坑）——**需要 A/B 实测权衡**：PUBLIC 下 `/ui` 是否真能读到虚拟屏、浮窗/设置承载是否被隐藏。

### 假设 C：`getWindows()` 本身在多显示下的版本限制

- AOSP 早期（API < 30/31）`AccessibilityService.getWindows()` 只返回默认屏窗口；Android 12+ 开始支持多显示窗口与 `AccessibilityWindowInfo.getDisplayId()`。
- 设备是 Android 13，理论上具备多显示窗口 API；若在原生 AOSP 上同样读不到，则假设 C 成立（系统层对该私有屏不开放）；若原生可读而 MIUI 不可，则假设 A 成立。

### 假设 D：窗口归属/焦点（OwnFocus / 输入焦点）影响 a11y“交互窗口”判定

- sdk≥34 才加 `FLAG_OWN_FOCUS`；13 上虚拟屏无自有焦点。若无焦点窗口不被 a11y 视为“交互窗口”，即使有窗口也不会出现在 `FLAG_RETRIEVE_INTERACTIVE_WINDOWS` 结果里。13 上可尝试把 `FLAG_OWN_FOCUS` 等标志提前加入做 A/B。

**结论**：大概率是 **A（ROM 裁剪）+ B（私有屏类型）共同作用**；需要一次“原生 13 对照 + PUBLIC/PRIVATE + OWN_FOCUS 开关”的组合矩阵实验来拆解，见 §5。

## 5. 取证与实验计划（待真机联网执行）

1. **窗口/display 证据**：
   `dumpsys window displays`（确认虚拟屏 displayId、`mVirtualDisplay` 项）；
   `dumpsys accessibility`（确认 a11y 已感知到的 displayId 集合 / available windows）。
2. **onAccessibilityEvent 抓虚拟屏事件**：在 `MfaAccessibilityService.onAccessibilityEvent` 里记录 `event.displayId != 0` 的 `typeWindowStateChanged/contentChanged`，确认系统**是否**向本服务投递虚拟屏事件（投递=窗口在 a11y 视野内，只是 `windows()` 聚合时被过滤）。
3. **标志 A/B 矩阵**：
   - 当前（PRIVATE + OWN_CONTENT_ONLY）基线；
   - `+FLAG_OWN_FOCUS`（Android13 提前启用）；
   - 改 `FLAG_PUBLIC`（评估 a11y 可见性 vs 投屏保护副作用）；
   - 各组合下调用 `/ui` 看是否出现 `displayId!=0`。
4. **跨 ROM 对照**：如在原生 Android 13 / 其它厂商 ROM 上运行同一 APK，记录 `/ui` 是否含虚拟屏，区分“ROM 限制”还是“平台限制”。
5. 结论落到本节/§4 的假设剔除。

## 6. 影响与当前规避

- **影响**：外部智能体无法做元素级寻址（按 text/bounds 找按钮），只能坐标寻址。
- **已生效规避（配合 009-mcp-tools）**：
  - `screen_capture` 截虚拟屏帧 → 交给视觉模型识别元素与坐标；
  - `status` 返回虚拟屏真实分辨率（`vScreenWidth/Height/Dpi`）作为坐标计算权威口径；
  - `screen_tap / screen_swipe / screen_key / screen_text` 按坐标/焦点注入完成交互；
  - 链路在 009 测试用例中已验证可用（计算器/天气/日历/自动化）。
- **文档口径**：`docs/MCP.md`、`docs/API.md`、`specs/009-mcp-tools/*` 已统一为“以截图 + 视觉定位，坐标以 status 分辨率为准”。

## 7. 其它被排除的方向（已评估不可行 / 不优先）

| 方向 | 说明 | 结论 |
|---|---|---|
| `UiAutomation` | 需 `INJECT_EVENTS` / 系统签名权限 | 免 root 不可行 |
| 应用内直接读第三方 App View 树 | 目标 App 是第三方进程的 View | 架构上不可行 |
| 新做一个 IME | 改用户默认输入法，侵入大 | 仅作为“文本输入”备选，与读树无关 |
| 用 `/frame` + 本地 OCR | 与当前“截图+视觉”等效 | 已由视觉模型方案覆盖 |
