# 主屏承载可行性方案（Main-Screen Hosting Feasibility）

术语（以此为准）：
- **虚拟屏承载模式（Display Mode A，简称 Mode A）**：承载 App 在**虚拟屏**（用户不可见），本应用 UI 在**主屏**（用户可见配置界面）。
- **主屏承载模式（Display Mode B，简称 Mode B）**：承载 App 在**主屏**（用户可见），本应用 UI 在**虚拟屏**或不可见（headless / `FLAG_SECURE`）。

> 状态：**设计提案 / 评估中（未实现）** ｜ 最后更新：2026-11-09
> 适用工程：ManagedFloatingApp ｜ 约束沿用总纲：免 root、arm64-v8a、minSdk 24、仅局域网/USB、敏感信息不入档。
> 本文档由原《问题记录.md》升级而来：第 1–4 节保留原「ui_read 虚拟屏不可读」问题分析，第 5 节起为针对
> “翻转承载（本应用上虚拟屏、目标 App 上主屏）”方案的可行性评估。

---

## 1. 问题背景（源自问题记录 001）

**`ui_read` / `GET /ui` 读不到被托管虚拟屏 —— 仅返回主屏。**

- 承载任意 App（计算器/天气/日历）到私有虚拟屏后，MCP `ui_read` / REST `/ui` 返回的元素树**只有 `displayId=0` 的主屏窗口**（状态栏 clock / 电量 / WLAN 等 `com.android.systemui`），被托管 App 的控件一个都读不到。
- 实测证据：一次调用返回 4701 字节，全部 `"displayId":0`。
- 影响：外部智能体无法“元素级寻址”（按 text/bounds 操作），只能依赖「截图 + 视觉定位 + 坐标」。
- 现状规避：`screen_capture`（虚拟屏出帧正常）+ `status`（真实分辨率）+ `screen_tap/swipe/key/text`（坐标注入），在 009-mcp-tools 用例中已验证可用。

## 2. 源码链路（代码事实）

```
MCP ui_read / REST GET /ui
  → ScreenController.readUi() → AppScreenController.uiReader
  → MfaAccessibilityService.instance?.dumpUi()
  → 遍历 AccessibilityService.windows（getWindows()）→ 元素树
```

- 读树**完全依赖 `getWindows()`**；该列表不含虚拟屏窗口时即无数据；`rootInActiveWindow` 兜底也只在主屏。
- a11y 服务已开 `FLAG_RETRIEVE_INTERACTIVE_WINDOWS` + `FLAG_INCLUDE_NOT_IMPORTANT_VIEWS`，仍读不到 ⇒ 问题在上游（系统/ROM 没把虚拟屏窗口喂给无障碍栈，或虚拟屏类型被 a11y 排除）。
- 虚拟屏由 `VdHelper` 以 `FLAG_OWN_CONTENT_ONLY|SUPPORTS_TOUCH|ROTATES_WITH_CONTENT|DESTROY_CONTENT_ON_REMOVAL|TOUCH_FEEDBACK_DISABLED`（PRIVATE，非 PUBLIC）创建；注入走 `input -d <虚拟屏> …`、截帧走紧贴该屏的 `FrameHub`（Surface+ImageReader）。**窗口存在（能截图/能注入），仅无障碍层未暴露。**

## 3. 根因假设（需真机取证）

| 假设 | 说明 | 概率判断 |
|---|---|---|
| A ROM 无障碍裁剪 | MIUI 的 AccessibilityManagerService 只维护主屏窗口列表 | 最可能 |
| B PRIVATE 屏被 a11y 排除 | 私有虚拟屏不注册无障碍窗口 token | 很可能（与 A 叠加） |
| C 多显示 API 限制 | `getWindows()` 在多显示下仅返回主屏 | 需在原生 13 对照确认 |
| D 焦点标志 | 13 上无 `OWN_FOCUS`，非交互窗口不进 `INTERACTIVE_WINDOWS` | 低 |

取证计划（真机在线后执行）：`dumpsys window displays` / `dumpsys accessibility`；`onAccessibilityEvent` 抓 `displayId!=0` 事件；PUBLIC/PRIVATE × OWN_FOCUS 标志 A/B 矩阵；跨 ROM 对照。→ 详见「第 9 节」。

## 4. 一句话结论（问题部分）

**“在私有虚拟屏上既要隔离又要有结构化可读”在 MIUI 上是系统性冲突**：改标志只能碰运气（A/B 待验证），真正能一次解决“可读”的是把承载目标切到**无障碍完全支持的主屏** —— 即下面要评估的方案，但代价是产品语义反转。

## 5. 拟议方案（翻转承载）

> 原文：本应用在启动服务、创建虚拟屏、承载 App 后，把本应用自己放到虚拟屏中，让承载的 App 放在主屏。
> 对应 API、MCP、WebRTC、MJPEG 等，都改为针对主屏。

### 5.1 目标拓扑对比

| 项 | Mode A（虚拟屏承载，现状） | Mode B（主屏承载，拟议） |
|---|---|---|
| 承载 App | 虚拟屏（用户不可见） | **主屏 displayId=0（用户可见）** |
| 本应用 UI/服务 | 主屏（配置界面可见） | 虚拟屏（原则上用户不可见，可选） |
| 帧源 | shell 私有 VirtualDisplay → `FrameHub` | **MediaProjection 捕获主屏 → `FrameHub`（投影 VirtualDisplay）** |
| 读屏 | a11y `windows()`（虚拟屏读不到） | a11y `windows()`（主屏可读）✅ |
| 操作 | `input -d <虚拟屏>`（脆、版本敏感） | **a11y `dispatchGesture` + `input -d 0` 兜底**（更稳）|

### 5.2 关键事实澄清

- **MediaProjection 也会“建虚拟屏”**，但那是**捕获型虚拟屏**（把主屏画面镜像进我们提供的 `ImageReader.surface`），与现在的**宿主型私有虚拟屏**不同。改造的实质 = **替换“屏幕来源”，`FrameHub` 主程序几乎不变**（仍是 `Surface+ImageReader+latestPng/copyRgba`），MJPEG/WebRTC/本地预览三个消费方无需改动。

## 6. 可行性分层评估

### 6.1 目标 App 放主屏——多维度可行性

| 能力 | 可行性 | 说明 / 阻塞 |
|---|---|---|
| 无障碍读树（ui_read） | ✅ 直接可用 | 主屏窗口在 `getWindows()` 内，现有 `dumpUi` 不加改就能读目标 App 控件；**问题 001 消失** |
| 无障碍手势（替代注入） | ✅ 需小改 | a11y 配置补 `android:canPerformGestures="true"`，用 `dispatchGesture` 做 tap/swipe/scroll/长按：不依赖 shell、比 `input -d` 稳，是当前推荐做法 |
| `input -d 0` 兜底注入 | ✅ 可用 | 主屏为默认 display，`input` 可用；但与用户触屏/键盘互相干扰，且受版本影响 |
| 帧/视频源 | ⚠️ 必须换实现 | 不能用宿主私有屏 Surface；**必须 MediaProjection**（一次性授权弹窗 + token 生命周期 + Android 14 起需 `mediaProjection` 前台服务类型） |
| 目标 App 可见性 | ⚠️ 产品语义反转 | 目标 App 出现并占用用户主屏，用户可看到自动化过程；不是“后台屏” |

### 6.2 “把本应用自己放到虚拟屏”——必要性评估

**结论：技术上可行，但缺省条件下没必要；仅当同时满足“Mode B 又要常驻可见的助手 UI”且有“不让助手 UI 进入主屏录制流”的需求时才需要。**

- 可行：`am start --display <id>` / `Display.moveToDisplay` 可把本应用窗口放到虚拟屏。
- 无收益点：本应用主程序是**前台服务 + 可 headless**；Mode B 完全可以用“无 UI / 悬浮窗（`FLAG_SECURE` 让它在投影里变黑）”来避免污染录制，不必整 App 迁移。
- 副作用：配置界面/任务列表会从主屏消失，用户“当面配置/查看状态”的能力被破坏（违背 006/101 的用户用例）。
- 结论：**该步骤从方案里去掉**（或降级为可选项），不能作为解决 ui_read 的组成部分。

### 6.3 对现有链路（API/MCP/WebRTC/MJPEG）的改造面

| 链路 | 现状 | Mode B 改造 |
|---|---|---|
| `GET /frame`、`/stream`(MJPEG) | `controller.captureFrame()` / `frameSource().latestPng()` | 帧源换成投影型 ImageReader，消费方不变 |
| WebRTC | `frameSource().copyRgba()` 走 H.264 | 同上，帧源换源即可 |
| `ui_read` | 读主屏（现状） | **自动变成读目标 App（主屏）**，行为吻合 |
| `screen_tap/swipe/key/text` | `input -d <虚拟屏>` | 改 a11y 手势优先 + `input -d 0` 兜底；`screen_text` 非 ASCII 剪贴板+粘贴流程不变 |
| `app_launch` | `am start --display <虚拟屏>` | 改 `am start`（主屏），并负责前置到前台 |
| `status` | 虚拟屏尺寸 | 增加 mode 字段 + 主屏尺寸；坐标口径随之切换 |
| 会话状态机 | 仅 Mode A | 新增 Mode B 授权态（未授权/已授权）；可并行存在 |

**共性问题（隔离丢失）**：目标 App 在主屏后，用户切到自己的 App、来电、键盘都会改变主屏内容 → `ui_read` 与视频流反映的是“当时主屏”，而不是“我们的目标 App”。**无人值守自动化会在中途读/录/操作了错误界面**。这是 Mode B 无法回避的运营风险。

### 6.4 隐私与安全（结构性变化，需决策）

- 现状：只录私有虚拟屏 —— 用户主屏的微信/相册/密码/通知**绝不会**进入视频流；安全边界小且清晰。
- Mode B：MediaProjection 默认抓**整块主屏**（含通知、输入法、用户自开应用、用户聊天记录），全部进入 MJPEG/WebRTC/MCP。**隐私边界与现方案相反**。
- 缓解：仅限局域网/USB + token（既有）；用户需在 Mode B 主动授权并知悉“屏幕将被投录”；可用 `FLAG_SECURE` 处理本应用自身窗口；Android 14+ 有 `MediaProjectionConfig` 局部/排除捕获可进一步限定范围。
- 建议：**文档与 UI 明示；不推荐无人值守后台跑 Mode B**。

### 6.5 授权与人机交互

- MediaProjection 无法静默授权：必须弹系统“开始录制/投屏”确认框，用户点一次；token 在投影停止/重启后失效，需重新授权（Android 10+ 每次投影一令牌）。
- Android 14 起 `createVirtualDisplay` 须在 `foregroundServiceType="mediaProjection"` 的前台服务里调用 —— manifest + Manifest.permission.FOREGROUND_SERVICE_MEDIA_PROJECTION。
- 用户在场时“自动化 vs 用户操作”会互相打架；宜提供“暂停/锁定”交互。

## 7. 与现有模式的关系 —— 建议“双模式并存”

主屏承载**不适合整体替换**私有虚拟屏后台托管（会丢掉“私密后台屏 + 用户可正常用自己手机 + 无人值守”的核心价值），但它是业内主流“AI 手机智能体”的架构（MediaProjection + 无障碍 + 手势）。建议：

| 模式 | 触发场景 | 关键能力 |
|---|---|---|
| **Mode A（虚拟屏承载，默认）** | 无人值守 / 用户用自己的手机 / 不打扰用户 | 截帧+坐标注入（当前链路）；ui_read 不强依赖 |
| **Mode B（主屏承载，新增）** | **用户在场**，AI 协同操作前台 App（如代点外卖/查天气/演示），且需要结构化读屏 | MediaProjection 截主屏 + a11y 读树/手势 + input 兜底；ui_read/元素级寻址全可用 |

- Mode B 作为独立开关/请求进入，与会话状态机增加“授权态”；两种模式不同时对同一对象操作。
- 坐标口径：MCP `status` 增加 `mode`；`screen.*` 按当前 mode 分派目标显示。

## 8. 模式切换交互与实现设计（Mode A ⇄ Mode B）

> 依据用户需求细化：`应用`页点图标默认 Mode A；呈现区右上角新增「主屏」按钮切 Mode B；
> 系统任务栏通知双向切换。**注意**：用户给出的“切回 Mode A”动作清单与 Mode B 完全相同（应属笔误），
> 按拓扑应为**本应用回主屏、承载应用回虚拟屏**，本文档按此纠正。

### 8.1 交互设计

| # | 位置 | 动作 |
|---|---|---|
| 1 | `应用`页 图标网格 | 点图标默认进入 Mode A（幂等，首启默认） |
| 2 | `应用呈现`右上角（现状：嵌入/全屏/浮窗 + 关闭行内） | 新增「主屏」按钮 → 切 Mode B。注意它是**承载模式**而非呈现模式，建议独立样式/分组，避免与嵌入/全屏/浮窗混淆 |
| 3 | 系统任务栏（通知） | 常驻一条：`ManagedFloatingApp模式切换：虚拟屏承载 / 主屏承载`，点击（PendingIntent 广播）切到另一模式，双向互切 |

### 8.2 各动作可行性

| 动作 | 可行性 | 实现要点 / 阻塞 |
|---|---|---|
| 默认 Mode A | ✅ | `PresentationHub`/`ServerConfig` 记录 `mode`，首启默认 A |
| 「主屏」按钮触发切 B | ✅（需用户交互一次） | 走 `MediaProjectionManager.createScreenCaptureIntent()` 的 ActivityResult 弹系统授权；**无法静默授权**；被拒/失败回滚 Mode A |
| Android 14+ 兼容 | ⚠️ 前置 | `foregroundServiceType="mediaProjection"` + `FOREGROUND_SERVICE_MEDIA_PROJECTION`；`createVirtualDisplay` 必须在投影前台服务内调用 |
| 承载 App 搬屏 | ✅ | B：`am start -n <pkg>/<act>`（主屏前置）；A：`am start --display <vd>`（沿用 VdHelper.launch）；注意 task 残留（见 8.3-1） |
| 本应用搬屏 | ⚠️ 两案 | ① 任务迁移：`ActivityOptions.setLaunchDisplayId` / `am start --display` 重载——**难点**：旧 task 残留、Dialog/MediaProjection 授权弹窗归属；② 不迁移 + `FLAG_SECURE`（投影里显示黑块、UI 不泄漏）——**首版推荐②**；把“本应用放虚拟屏”降为可选优化 |
| 推流切换 | ✅ | 帧源抽象：`ScreenController.frameSource()` 在 A（私有屏 `FrameHub`）与 B（MediaProjection 捕获 `FrameHub`）间切换；MJPEG/WebRTC/`/frame` 只认接口，消费方不变 |
| API 指向切换 | ✅ | `status` 增 `mode` 与对应分辨率；`screen_tap/swipe/key/text` 按 mode 分派（B：a11y 手势优先 / `input -d 0` 兜底；A：`input -d <vd>`）；`ui_read` 天然指向主屏 |
| 通知条目 | ✅ | 前台通知 + ContentIntent（PendingIntent 广播切模式）；切换后立即可点回切 |
| 会话 / 自动化保持 | ⚠️ 约束 | **正在运行自动化任务时禁止切换**；切换不销毁会话与承载 App 实例（同一实例换屏） |

### 8.3 需原型验证的关键点

1. **Activity 跨屏迁移**：`am start --display` 对主 Activity 的 task 残留 / 重复实例；Dialog（权限、MediaProjection 授权）归属到哪个 display。
2. **MediaProjection 生命周期**：token 失效（重启 / 杀进程 / 投影停止）→ 自动回 A 并提示；旋转 / 分辨率变化 → 重建投影。
3. **A⇄B 往返连续性**：私有 VD 在 Mode B 期间保持存活以便快速回 A；投影帧源与私有屏帧源严格不串（状态机区分）。
4. **多客户端**：MJPEG / WebRTC 全局跟随模式（单一全局承载模式），切模式所有客户端随帧源一起切换/续推。
5. **坐标口径**：`status.w/h` 与 `screen_capture` 分辨率随 mode 变化；009 脚本按 `screen.info` 等比换算逻辑不变，天然适配。

### 8.4 建议状态机

```
Mode A（默认）
  │  [主屏按钮 | 通知「体验主屏承载」]
  ▼
授权（MediaProjection 系统弹窗）
  ├─ grant ──► Mode B（建投影帧源、承载 App 前置主屏、本应用 UI 不迁移+FLAG_SECURE、更新通知文案）
  ├─ deny / error ──► 回 Mode A（提示）
Mode B
  │  [通知「体验虚拟屏承载」]
  ▼
Mode A（释放投影帧源、承载 App 回私有虚拟屏、恢复虚拟屏推流、更新通知文案）

规则：`runningTaskId != null` 时禁止切换；任意时刻仅存在一个全局承载模式。
```

### 8.5 与呈现模式正交性

- 承载模式（A/B）≠ 呈现模式（嵌入/全屏/浮窗）：Mode B 下“全屏/浮窗”呈现的是**主屏捕获画面**，Mode A 下是**私有屏画面**。
- 首版建议 Mode B 固定配合“全屏 / 无 UI”，减少承载×呈现叠加的边界问题；后续再放开组合。

## 10. 与“虚拟屏内继续深挖”的决策分叉

在动手 Mode B 之前，建议先花 ~0.5 天执行问题 001 的取证矩阵（PUBLIC/PRIVATE × OWN_FOCUS × 跨 ROM），若 **A/B 矩阵能低成本让虚拟屏可读**，则 Mode A 直接受益、可暂缓 Mode B；若确认是 ROM 硬裁剪（A），Mode B 即为较优解。**两条路互不冲突，可先后推进。**

## 11. 风险清单

1. **隐私反转**：主屏全量投录（最高优先，需产品拍板 + 用户明示）。
2. **隔离丢失**：无人值守时可能读/录/操作错误界面（建议 Mode B 仅限用户在场）。
3. MediaProjection 授权断链：token 失效、服务被杀、屏幕旋转 → 需状态机处理“重新授权/重建投影”。
4. Android 14+ 前台服务类型与权限的兼容分支。
5. 用户与自动化同时操作主屏的冲突（需暂停/锁定时序）。
6. 既有 Mode A 链路回归：改动集中在帧源层，需保持 A 模式不变。

## 12. 决策记录

- 2026-11-09：评估完成。**结论：方案可行，但应作为“主屏承载模式（Mode B）”与现有后台虚拟屏模式并行，不整体替换**；“本应用自己放虚拟屏”从方案中剔除（可视需要作为避免助手 UI 进入录制的可选项）。
- 2026-11-09（续）：细化模式切换交互与状态机（§8）。核定术语：Mode A=虚拟屏承载、Mode B=主屏承载。
